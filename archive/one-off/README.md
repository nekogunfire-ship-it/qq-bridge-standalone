# 归档：一次性排查脚本

这里存放**已完成任务的排查/验证脚本**。它们不是工具，不要在正常使用或发布版里运行 ——
多数要求桥接正在运行、且会**真的往 QQ 发消息**。

保留原因：这些脚本记录了问题是怎么被定位的（每一步对照、每一次假设的验证），
将来遇到同类问题（图片渲染、OneBot 协议形状、DSH 协议变更）可以直接翻出来改改再用。

排序按文件名。每个脚本的"服务于"是它当年要解决的问题，"结论"是那次排查得到的答案。

## 1. `diag-ab-image.mjs`

- **用途**：A/B 定论测试：同一张图、同一个私聊目标，分别用 OneBot HTTP 直连与桥接端点发送， 并各自打印 SnowLuma 日志里的渲染结果。判定「桥接路径是否真的发不出图片」。
- **服务于**：同上：确认是桥接路径的问题而非 SnowLuma
- **结论**：A/B 对照证明 OneBot 直连能发、桥接路径发不出，锁定问题在桥接侧。
- **体积**：3106 字节

## 2. `diag-empty-text.mjs`

- **用途**：验证核心假设：SnowLuma 对「图片 + 空文本段」这种组合是否整条渲染坏。 对照四种组合，确认空 text 段是不是元凶。
- **服务于**：同上：验证"图片 + 空文本段"是否整条渲染坏
- **结论**：确认空 text 段是元凶之一，修复时加了空文本守卫。
- **体积**：2472 字节

## 3. `diag-image-multiseg.mjs`

- **用途**：判定「图片段 + 文字段」的多段数组是否就是失败原因（桥接走的是这条路）。 对照：单段图片 / 图片+文字 / 文字+图片。
- **服务于**：同上：多段数组是否就是失败原因
- **结论**：确认单段图片可行、图片+文字也可行，问题不在多段本身而在构造方式。
- **体积**：2970 字节

## 4. `diag-image-size-sweep.mjs`

- **用途**：按图片体积扫描：找出 SnowLuma 图片上传在多大开始失败。 用同一张图的多个缩放/放大版本，逐个发送并打印结果与渲染行。
- **服务于**：同上：图片体积是否有上限
- **结论**：排除了"图片过大导致失败"这一假设。
- **体积**：3973 字节

## 5. `diag-image-source-field.mjs`

- **用途**：对照测试：image 段只用 file / 只用 url / 两者都给 / 用 data: URL， 找出 SnowLuma 实际接受哪种来源字段。
- **服务于**：同上：image 段该用 file 还是 url
- **结论**：确定用 file 传 base64:// 是正解。
- **体积**：4527 字节

## 6. `diag-onebot-format.mjs`

- **用途**：判定 SnowLuma 到底接受哪种 message 形式：纯文本字符串 / 结构化数组（文本段）/ 结构化数组（图片段）/ 带 message_format 参数。每次发送后打印 SnowLuma 新增日志。
- **服务于**：同上：确认 SnowLuma 接受哪种 message 形式
- **结论**：证明必须用结构化数组，纯字符串与 message_format 参数都不行。
- **体积**：3111 字节

## 7. `diag-onebot-image.mjs`

- **用途**：绕开桥接，直接用 OneBot HTTP 给 SnowLuma 发一张极小的 PNG， 对照「base64://」与「本地文件路径」两种 file 来源，判断哪一种能真正发出图片。
- **服务于**：同上：确认 SnowLuma 接受哪种 file 来源
- **结论**：证明 base64:// 可行，本地路径不可行。
- **体积**：4378 字节

## 8. `diag-onebot-proxy.mjs`

- **用途**：OneBot 请求记录代理：监听本地端口，把请求原样转发到真实 SnowLuma， 并把「桥接实际发出的 body」写进日志文件。
- **服务于**：同上：抓桥接实际发出的 body
- **结论**：本地代理记录到桥接发出的原始请求，直接看到错误构造。
- **体积**：3721 字节

## 9. `diag-send-image.mjs`

- **用途**：诊断用：直接调用桥接的 /api/socialV2/send-image 发送一张真实图片到指定会话， 打印响应，便于与 SnowLuma 日志对照定位「图片变成 [object Object]」的问题。
- **服务于**：QQ 发图渲染成 [object Object]
- **结论**：定位到桥接调用 onebotSend 时把 segments 数组当字符串传参。已修复为 sendSegments()。
- **体积**：2255 字节

## 10. `diag-verify-base64.mjs`

- **用途**：验证：桥接构造的 image 段里的 base64 是否与源文件字节完全一致。 大字符串拼接（'base64://' + buf.toString('base64')）在某些实现下会截断/损坏，
- **服务于**：同上：base64 字符串拼接是否被截断
- **结论**：逐字节比对确认 base64 与源文件一致，排除编码损坏。
- **体积**：2652 字节

## 11. `diag-verify-fix.mjs`

- **用途**：验证 bridge.js 修复后的段构造：sendSegments 应收到 [image]（无空 text 段）。 本脚本**直接复刻修复后的构造逻辑**并通过 OneBot 发出，证明该段结构能真正送达图片。
- **服务于**：同上：验证修复后的段构造真的能送达
- **结论**：复刻修复后的逻辑实发成功，作为修复生效的证据。
- **体积**：2879 字节

## 12. `probe-015.mjs`

- **用途**：探测 DSH 0.1.5-rc.1 的 Web API 协议表面（只读，不改动 DSH 状态）。
- **服务于**：DSH 0.1.5-rc.1 升级适配
- **结论**：探明新版 Web API 协议表面后，适配已完成；后续版本变更可临时重跑参考。
- **体积**：3765 字节

## 13. `probe-events.mjs`

- **用途**：端到端验证：remote.mux 事件流 + turn 收集 + 工具调用事件形状。 只读观测：创建一个探测会话，注入一条简单 prompt，打印收到的事件类型与结构。
- **服务于**：remote.mux 事件流协议
- **结论**：事件形状已确认并落到 dsh-client.js；此探针用于将来协议变更时复核。
- **体积**：5203 字节

## 14. `probe-mcp-tools.mjs`

- **用途**：说明（为什么这里不是 stdio 探针）： 最初这个脚本用 MCP 官方 SDK 的 StdioClientTransport 去 spawn
- **服务于**：验证 MCP 工具注册面（失败方案）
- **结论**：用 StdioClientTransport spawn 子进程在文件沙箱里必然 EPERM，脚本永远跑不通。文件头已写明「留着只会误导」；注册面验证改由 scripts/test-comfy-tools.mjs 承担。
- **体积**：1014 字节

## 15. `probe-rpc-compat.mjs`

- **用途**：对比探测：逐条验证桥接实际使用的 RPC 参数形状在新版 DSH 上是否被接受。
- **服务于**：DSH 0.1.5：逐条验证桥接使用的 RPC 参数形状仍被接受
- **结论**：全部参数形状通过，适配完成。
- **体积**：5543 字节

## 16. `probe-workspace.mjs`

- **用途**：验证 workspace/session RPC 参数形状与返回值结构（对照 bridge.js 实际用法）。
- **服务于**：DSH 0.1.5：workspace/session RPC 参数形状与返回结构
- **结论**：形状确认并对照 bridge.js 实际用法验证通过。
- **体积**：3754 字节

## 17. `verify-dsh-015-adaptation.mjs`

- **用途**：DSH 0.1.5 适配总验证：一次性跑完所有关键断言，输出 PASS/FAIL 清单。 不依赖 SnowLuma；不修改任何状态（探测会话会被 archive）。
- **服务于**：DSH 0.1.5 适配总验证（一次跑完所有关键断言）
- **结论**：PASS，升级适配收官；曾作为 npm run verify:adaptation 使用，该 npm 脚本已随归档一并移除。
- **体积**：12014 字节

## 18. `probe-launcher-service-process.ps1`

- **用途**：把 `qq-bridge-launcher.ps1` 里的 `Get-ServiceProcess`（用 `Get-CimInstance Win32_Process` 按命令行匹配进程）单独抠出来跑，判断"启动器里查不到进程"是代码问题还是**权限问题**。
- **服务于**：2026-09-24 排查"启动器体检总说服务没在跑，但端口明明在监听"。根因是权限：服务由提权启动，非提权上下文枚举不到它们的命令行 —— 与 2026-09-26 桌面版看门狗自检撞到的是同一件事（见 `scripts/test-desktop-launcher.mjs` 里那条 SKIP 分支）。
- **结论**：代码没问题，是权限。正式工具请看仍在维护的 `tools/probe-launcher.mjs`。
- **体积**：1657 字节
- **备注**：原先放在 `tools/runtime/` 下，而那个目录是启动器自动生成的运行时目录（`init.json` / `launched-pids.json` / `*.log`），整个目录不该入库 —— 清理时把它挑出来归档到这里。

## 注意

- 这些脚本可能引用**当时的**文件结构或已移除的功能，不保证现在还能直接跑通。
- 其中直接调 OneBot / 桥接发送接口的脚本（`diag-onebot-*`、`diag-send-image`、
  `diag-ab-image`、`diag-verify-fix`）**会真的发出 QQ 消息**，重跑前请先确认目标会话。
- 想复查 safetensors 架构（模型/LoRA 兼容性判断）请用仍在维护的
  `scripts/inspect-safetensors.mjs`，不要翻这里的旧脚本。
